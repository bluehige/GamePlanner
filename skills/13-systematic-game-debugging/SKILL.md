# Systematic Game Debugging

버그를 보고 즉시 코드를 바꾸지 않는다. **재현 → 관찰 → 경계 추적 → 단일 가설 → 최소 수정 → 원증상·회귀 검증** 순서를 강제한다.

## 사용 시점

- 크래시, 입력 불능, 상태 꼬임, 전투 오동작, 저장 손상, 화면 불일치
- 같은 문제를 여러 차례 수정했지만 다시 발생할 때
- 특정 환경·세이브·프레임 순서에서만 재현될 때
- 자동 테스트는 통과하지만 실제 게임에서 실패할 때

## 입력

- 원문 제보와 기대 동작
- 정확한 빌드, branch, SHA, 플랫폼, 하드웨어
- 재현 세이브·시드·입력 순서·영상·로그
- 관련 Work Order, Change Impact, Wiki 사건
- 정상 동작 기준 버전이 있으면 해당 버전

## 절차

1. 기대 동작과 관찰 동작을 분리한다.
2. 재현 절차를 최소화하고 재현률을 기록한다.
3. 기준 빌드와 문제 빌드에서 같은 절차를 실행한다.
4. 다음 경계를 순서대로 추적한다.

```text
입력 장치/명령
→ UI·조작 상태
→ 게임 상태·상태 머신
→ 규칙·시뮬레이션
→ 애니메이션·렌더·오디오 표현
→ 콘텐츠·리소스 참조
→ 저장·로드·네트워크 경계
```

5. 각 경계의 입력값, 출력값, 소유자, 시간 순서를 기록한다.
6. 정상 사례와 실패 사례의 첫 번째 차이를 찾는다.
7. 한 번에 하나의 반증 가능한 가설을 세운다.
8. 가설을 검증하는 최소 관찰 또는 테스트를 추가한다.
9. 근본 원인이 확인된 뒤 최소 수정한다.
10. 원래 재현 절차, 관련 회귀, 저장·플랫폼 조건을 다시 검증한다.
11. 사건 기록과 예방 규칙 후보를 `17-game-dev-memory`에 넘긴다.

## 근본 원인 분류

- `requirement_misread`: 사용자·기획 의도 오해
- `stale_context`: 오래된 문서·브랜치·데이터 사용
- `state_transition`: 잘못된 상태 전이 또는 누락
- `ownership`: 동일 상태를 여러 곳이 소유
- `timing_order`: 비동기·프레임·이벤트 순서 문제
- `data_reference`: ID·경로·리소스 참조 문제
- `save_migration`: 저장 버전·마이그레이션 문제
- `platform_environment`: 플랫폼·드라이버·권한·경로 차이
- `test_gap`: 실제 실패 경로를 검사하지 않은 테스트
- `architecture`: 국소 수정으로 해결할 수 없는 구조 문제

## 하드 게이트

- 재현하지 못한 문제를 해결됐다고 선언하지 않는다.
- 로그 한 줄만 보고 원인을 확정하지 않는다.
- 여러 가설을 한 번의 수정에 섞지 않는다.
- 증상을 숨기는 재시도·지연·널 체크를 근본 수정으로 포장하지 않는다.
- 세 차례의 독립적인 수정이 실패하면 네 번째 임시 패치를 하지 않고 아키텍처와 계약을 재검토한다.
- 디버그 로그와 진단 코드는 출시 전 제거 또는 비활성 정책을 정한다.

## 완료 게이트

- 다른 사람이 같은 빌드에서 재현 절차를 실행할 수 있다.
- 실패 경로의 최초 이상 지점을 증거로 지목할 수 있다.
- 근본 원인과 증상 완화가 구분되어 있다.
- 수정 전 실패하고 수정 후 통과하는 검증이 있다.
- 원증상과 관련 회귀가 모두 새로 실행됐다.
- 사건이 Wiki에 편입될 준비가 됐다.
