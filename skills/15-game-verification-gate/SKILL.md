# Game Verification Gate

“완료”, “수정됨”, “정상”, “직관적”, “출시 가능” 같은 주장을 해당 주장에 맞는 **새로운 증거**와 연결한다.

## 사용 시점

- 모든 기능 구현·버그 수정·리팩터링의 완료 선언 전
- PR, 릴리스 후보, 외주 검수, 사용자 전달 전
- 자동 테스트와 실제 엔진 결과가 다를 가능성이 있을 때

## 입력

- Work Order와 수용 기준
- 변경 파일·씬·데이터 목록
- 기준 branch·SHA·빌드와 후보 branch·SHA·빌드
- 테스트 명령과 실행 로그
- 실제 엔진 캡처·입력 기록·세이브
- 관련 성능·플레이테스트 증거

## 주장-증거 매트릭스

| 주장 | 최소 증거 |
|---|---|
| 코드가 컴파일된다 | 해당 대상의 새 빌드 결과 |
| 테스트가 통과한다 | 전체 관련 테스트의 새 실행 로그 |
| 원래 버그가 수정됐다 | 동일 재현 절차의 수정 전 실패·수정 후 성공 |
| 기존 기능이 유지된다 | 영향 분석에서 정한 회귀 실행 |
| 씬·UI가 정상이다 | 실제 엔진 렌더와 입력 경로 |
| 저장이 호환된다 | 이전 저장 마이그레이션·라운드트립 |
| 성능이 목표를 만족한다 | 대상 하드웨어 프로파일 |
| 직관적·재미있다 | 동일 빌드의 실제 사용자 플레이테스트 |
| 출시 가능하다 | 18단계 릴리스 게이트 전체 증거 |

## 증거 수준

- `E0`: 문서·코드·설계 추정
- `E1`: 정적 검사·이미지·데이터 보고서
- `E2`: 실제 엔진 렌더·실행
- `E3`: 실제 입력, 상태 전환, 원증상·회귀 완주
- `E4`: 동일 빌드의 목표 사용자 플레이테스트
- `E5`: 대상 배포 환경의 설치·성능·업데이트·복구 검증

## 절차

1. 모든 수용 기준을 개별 주장으로 분해한다.
2. 각 주장에 필요한 증거 수준과 실행 방법을 배정한다.
3. 기준 SHA와 후보 SHA를 고정한다.
4. 정적 검사, 테스트, 빌드를 새로 실행한다.
5. 실제 엔진에서 핵심 경로를 실행한다.
6. 버그 수정은 원래 재현 절차를 그대로 반복한다.
7. 영향 분석의 회귀 목록을 실행한다.
8. 저장·성능·UX 주장은 해당 전문 게이트 결과를 연결한다.
9. 실패·미실행·환경 제약을 `UNKNOWN`이 아니라 명시적 상태로 남긴다.
10. 증거 묶음과 최종 판정을 작성한다.

## 판정

- `PASS`: 필요한 모든 증거가 현재 후보 빌드에서 충족됨
- `CONDITIONAL`: 비차단 항목과 명확한 후속 조건이 있음
- `FAIL`: 수용 기준 또는 치명적 회귀가 실패함
- `PENDING`: 필요한 증거를 아직 실행하지 못함

## 하드 게이트

- 이전 커밋이나 다른 빌드의 로그를 현재 증거로 재사용하지 않는다.
- 종료 코드만 보지 않고 실패·건너뜀·경고 수를 확인한다.
- 스크린샷 하나로 상호작용 성공을 주장하지 않는다.
- 자동 테스트로 재미·직관성·접근성 전체를 승인하지 않는다.
- “아마”, “보인다”, “코드상”을 PASS 근거로 사용하지 않는다.
- 검증하지 못한 항목을 성공으로 간주하지 않는다.

## 완료 게이트

- 모든 완료 주장에 현재 빌드의 증거가 대응한다.
- 기준과 후보를 혼동하지 않는다.
- 원증상, 회귀, 실제 엔진 경로를 구분해 검증했다.
- 미실행 항목과 한계가 드러난다.
- 판정이 증거 수준을 넘어 과장되지 않는다.
